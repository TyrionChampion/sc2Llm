# 非实时推进与调度加速（2026-10-18）

用户授权依次实施：取消非实时推进限速 → 集中并发请求 → 自适应步长。

## 实施行为

1. `arena/native_engine.py` 的非实时推进不再执行每轮固定约 0.1 秒的墙钟等待。实时观察与模型等待时的冻结帧轮询仍按 control_hz 限速。任何 planner 思考时仍然不发 RequestStep；暂停推进违规检查保留。`step(..., step_loops=N)` 使用同一个 N 向所有客户端并行推进，动态值限制为 1..224；投降收尾先于步长计算与校验。
2. `arena/step_scheduler.py` 的 `PlannerBatcher` 让主指挥和 BattleAgent 在 tick 中只更新执行器、接收回复和构建当前状态。随后集中准备双方到期请求，通过同一 threading.Event 闸门释放各自工作线程；准备后续请求失败时也释放已排队线程。各线程已有独立 mailbox，不等待其他模型回答后才开始请求。
3. 普通决策截止时间向后对齐到默认 2 游戏秒批次，最多延后 2 秒加一个循环。主指挥的紧急唤醒保留原截止时间；有基地/移动前线告警的战术决策不额外对齐。没有提前绕过原有 6/8/10 秒冷却。客户端暂不可请求时不会把引擎困在一帧步进。
   两客户端初始时钟可能相差一个循环，截止时间先换算到共同时间轴，派发时再换回各自时间。批次边界按整数循环计算，避免 22.4 循环/秒的取整让后续 20 秒周期不断额外延后一个批次；集成测试覆盖相差一帧的双方多轮并发。
4. `AdaptiveSteps` 从各方自己的合法观测选择共同步长：默认接敌 8、接近/行军最多 32、平静最多 64。可攻击的敌我单位靠近时、观察到自身掉血/死亡时、当前观测存在效果时缩小步长，并保持 2 游戏秒。采用双方最保守的共同选择；没有把另一方视野、单位或请求内容交给模型。未来请求到期前进一步裁剪至对应游戏循环，因此可能出现小于 8 的步长。
5. 实时模式不启用批次调度和自适应步长，继续使用原轮询控制。非实时报告新增 planner_batches、adaptive_steps、step_counts、last_step_loops 和 advance_wall_throttled，queued 请求日志含 request_batch，均不改变参赛模型或偷看战争迷雾。

## 配置

```bash
# 非实时默认启用：8/32/64 步长与 2 秒请求对齐
.venv311/bin/python native_llm.py --no-realtime --step-loops 8 --max-step-loops 64

# 固定步长；关闭时间对齐，但仍集中释放当前到期请求
.venv311/bin/python native_llm.py --no-realtime --no-adaptive-step --step-loops 8 --planner-batch-game-seconds 0
```

以上仅展示调度参数；正式模型、登录、种族、地图等仍由实际启动配置提供。

## 验证范围

- 控制器测试：动态 64/32/8/3 帧对所有参与者一致，暂停不推进，实时保持轮询限速，非实时推进不调用休眠；非法步长在发请求前拒绝。
- 真正的 Commander/BattleAgent 工作线程测试：四个客户端在同一屏障处会合，证明双方主指挥与战术请求并发；各自拿到自己的 world/squad，不混用观察。
- Native 主循环集成测试：使用受控引擎与真实 Commander，检查批次调度、自适应步进、暂停、最终统计、投降与退出保存路径。这些是接口行为验证，不是真实引擎性能数字。
- 使用 `testdata/ai_duel_latency/events.json` 的原始对局请求和基地告警时间，检查普通对齐延迟上限、紧急告警不额外等待批次，以及步进截止约束。

步长阈值属于保守初始设置，尚未用新配置的完整实战确定最优值。静态观测与本地客户端测试不能证明对战质量不变或单局加速倍数；需固定模型/地图/种子做后续实战对照。
